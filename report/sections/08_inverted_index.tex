\section{Inverted Index Evaluation}
\label{sec:index}

Three structures answer the same queries over the same corpus: a JSON file,
a folder of per-term files, and a MongoDB collection. Before their numbers
are interpreted, \cref{sec:equivalence-structures} showed that they answer
identically.

\subsection{Build scalability: elapsed time and memory growth}
\label{sec:index-scalability}

Each structure is built from batches of \fixed{25} to \fixed{10{,}000} books
(\cref{tab:workload}); every batch size is repeated and the mean is plotted.
Two series are shown (\cref{fig:scalability-elapsed,fig:scalability-memory}).

\begin{figure}[htbp]
    \centering
    \includegraphics[width=\textwidth]{scalability/scalability_elapsed.png}
    \caption{Build elapsed time versus batch size, mean of the repetitions
    listed in \texttt{scalability.csv}.}
    \label{fig:scalability-elapsed}
\end{figure}

\begin{figure}[htbp]
    \centering
    \includegraphics[width=\textwidth]{scalability/scalability_memory.png}
    \caption{Memory growth versus batch size. \textbf{memory\_mb is the RSS
    delta per batch}: the resident set size of the benchmark process after
    the build minus before it, sampled from \texttt{/proc/self/status}
    (Go/Rust/Java) or \texttt{psutil} (Python) --- see
    \cref{tab:metrics}. The callout ``Peak'' marks the \emph{largest plotted
    RSS delta} among the batch sizes, \emph{not} the peak resident memory of
    the process; that series is reported separately as
    \texttt{peak\_rss\_mb}.}
    \label{fig:scalability-memory}
\end{figure}

\paragraph{The 1{,}601 MB figure.}
In the earlier version of this report a batch was said to ``require 1{,}601
MB''. That number is the largest \emph{RSS delta} observed at the biggest
batch, and it must not be read as a memory requirement or as a process peak:
the delta measures growth caused by the build, while the process also holds
the already-loaded corpus and runtime overhead. The correct statement is:
\emph{at a batch of \pending{10000} books, the JSON build grew the
process's resident set by up to \pending{1601} MB (largest plotted delta),
while the process's peak resident set during that phase was
\pending{peak\_rss} MB}. Both series are in \texttt{scalability.csv};
neither includes the MongoDB server, whose footprint is reported in
\cref{sec:index-memory}.

\paragraph{RAM spikes and garbage collection.}
The evidence for the RAM-spike and GC remarks is the pair of columns
\texttt{peak\_rss\_mb} (sampled every \fixed{50} ms, so short spikes are
visible) and, for Go alone, the \texttt{memstats.csv} series
(\texttt{total\_alloc\_mb}, \texttt{gc\_cycles}) that counts allocation
volume and collection cycles during the same operations. Where a language
shows peak values well above its delta, that gap is the spike; where Go's GC
counter grows faster than its heap, that is the collection pressure. These
are observations from the CSVs, not extrapolations.

\subsection{Structures compared}
\label{sec:index-structures}

\paragraph{Where the bytes go.}
Beyond the per-structure numbers, the repository carries an interactive
sankey diagram of the storage breakdown (\texttt{charts/sankey/storage\_sankey.html},
generated by \texttt{storage\_sankey.py} from \texttt{disk\_usage.csv}) that
traces the corpus bytes from datalake files into each index component. The
static figures of this report quote its underlying numbers in
\cref{tab:datalake-storage,sec:index-structures}.

\paragraph{Query latency.}
Every structure answers the \fixed{30} shared queries, \fixed{5} times each
(\fixed{150} samples). The JSON index parses one file once and answers from
memory; the folder index opens one small file per term; MongoDB pays a
network/IPC round trip per term (\cref{fig:latency}).

\paragraph{On-disk footprint.}
\texttt{disk\_usage.csv} reports bytes, files and directories per structure
after indexing the identical corpus. For MongoDB the client-side file scan
is meaningless, so the server's own \texttt{collStats storageSize} is read
from the database itself and reported in the same table.

\subsection{Incremental updates}
\label{sec:index-updates}

Construction cost and update cost are different questions, so updates are
measured separately (\cref{fig:updates}): a base index of \fixed{25, 50,
250, 500, 1000} books is built untimed, then extended with \fixed{5} new
books (fresh synthetic IDs that cannot collide with the base), \fixed{5}
repetitions per base size. The plotted time is the update only.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=\textwidth]{scalability/scalability_updates.png}
    \caption{Incremental update time versus base index size, isolated from
    construction (\texttt{updates.csv}).}
    \label{fig:updates}
\end{figure}

\paragraph{The O(1) claim.}
The earlier report said MongoDB updates were ``O(1)''. The operation behind
the claim is \texttt{update\_book}: for each distinct term of the added book
it upserts one document, merging the book ID into that term's postings
array; the variable is the number of \emph{terms in the added book}, not the
size of the index. Whether the cost stays flat as the base grows is an
empirical question, and \texttt{updates.csv} answers it for the measured
sizes: \pending{update behaviour summary}. The claim is therefore replaced
by the observed curve; no constant-update behaviour is asserted beyond the
measured range, and larger bases remain unmeasured
(\cref{sec:limitations}).

\subsection{Memory and disk of the MongoDB structure}
\label{sec:index-memory}

All client-side memory series (\texttt{memory\_mb},
\texttt{peak\_rss\_mb}) describe the benchmark process only: the samplers
read \texttt{/proc/self/status} or \texttt{psutil} for their own PID, so
\texttt{mongod}'s resident memory is \emph{not} included in any client
figure. The server's cost appears in two places instead: its own storage,
measured through \texttt{collStats storageSize} on the benchmark database
(\texttt{search\_engine\_benchmark}, kept separate from the pipeline's
\texttt{search\_engine} datamart), and, qualitatively, as the extra process
a deployment must run. Any capacity statement about MongoDB in this report
refers to that measured storage size at the measured corpus, plus the
unmeasured server memory, which is listed as a limitation.
