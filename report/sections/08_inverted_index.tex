\section{Inverted Index Evaluation}
\label{sec:index}

Three structures answer the same queries over the same corpus: a JSON file,
a folder of per-term files, and a MongoDB collection. Before their numbers
are interpreted, \cref{sec:equivalence-structures} showed that they answer
identically.

\subsection{Build scalability: elapsed time and memory growth}
\label{sec:index-scalability}

Each structure is built from batches of \fixed{25} to \fixed{10{,}000} books
(\cref{tab:workload}); every batch size is repeated and the mean is plotted.
Two series are shown (\cref{fig:scalability-elapsed,fig:scalability-memory}).

\paragraph{The 1{,}601 MB figure.}
In an earlier version of this report a batch was said to ``require 1{,}601
MB''. That number was the largest \emph{RSS delta} observed at the biggest
batch, not a memory requirement and not a process peak: the delta is growth
caused by the build, while the process also holds the already-loaded corpus
and runtime overhead. In this snapshot the correct statement is: \emph{at a
batch of 10{,}000 books the JSON build grew the resident set by up to
1028.5 MB (largest plotted delta, the Java series), while the peak resident
set in that phase was 4591.0 MB}. Both series are in
\texttt{scalability.csv} and exclude the MongoDB server
(\cref{sec:index-memory}).

\paragraph{RAM spikes and garbage collection.}
The evidence is \texttt{peak\_rss\_mb}, sampled every \fixed{50} ms so short
spikes are visible, and, for Go alone, the \texttt{memstats.csv} series
(\texttt{total\_alloc\_mb}, \texttt{gc\_cycles}). A peak well above its delta
is the spike; a GC counter growing faster than the heap is collection
pressure. These are observations from the CSVs, not extrapolations.

\subsection{Structures compared}
\label{sec:index-structures}

\paragraph{Where the bytes go.}
The repository also carries an interactive sankey diagram of the storage
breakdown (\texttt{charts/sankey/storage\_sankey.html}, generated by
\texttt{storage\_sankey.py} from \texttt{disk\_usage.csv}) that traces the
corpus bytes from datalake files into each index component; the static
figures of this report quote the same numbers
(\cref{tab:datalake-storage,sec:index-structures}).

\paragraph{Query latency.}
Every structure answers the \fixed{30} shared queries, \fixed{5} times each
(\fixed{150} samples). The JSON index parses one file once and answers from
memory; the folder index opens one small file per term; MongoDB pays a
network/IPC round trip per term (\cref{fig:latency}).

\paragraph{On-disk footprint.}
\texttt{disk\_usage.csv} reports bytes, files and directories per structure
after indexing the identical corpus. For MongoDB the client-side file scan
is meaningless, so the server's own \texttt{collStats storageSize} is read
from the database itself and reported in the same table.

\subsection{Incremental updates}
\label{sec:index-updates}

Construction cost and update cost are different questions, so updates are
measured separately (\cref{fig:updates}): a base index of \fixed{25, 50,
250, 500, 1000} books is built untimed, then extended with \fixed{5} new
books (fresh synthetic IDs that cannot collide with the base), \fixed{5}
repetitions per base size. The plotted time is the update only.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.72\textwidth]{scalability/scalability_updates.png}
    \caption{Incremental update time versus base index size, isolated from
    construction (\texttt{updates.csv}).}
    \label{fig:updates}
\end{figure}

\paragraph{The O(1) claim.}
The earlier report said MongoDB updates were ``O(1)''. The operation behind
the claim is \texttt{update\_book}: for each distinct term of the added book
it upserts one document, merging the book ID into that term's postings array
--- so the variable is the number of \emph{terms in the added book}, not the
size of the index. Whether the cost stays flat as the base grows is
empirical, and \texttt{updates.csv} answers it for the measured sizes: the
JSON index grew 16--23$\times$ (base 25 to 1000 books), the folder index
1.6--2.2$\times$ and MongoDB 1.4--2.8$\times$ --- the single-file rewrite
tracks index size, the per-term files and the collection stay far flatter.
The claim is replaced by that curve; no constant-update behaviour is
asserted beyond the measured range (\cref{sec:limitations}).

\subsection{Memory and disk of the MongoDB structure}
\label{sec:index-memory}

All client-side memory series (\texttt{memory\_mb}, \texttt{peak\_rss\_mb})
describe the benchmark process only, so \texttt{mongod}'s resident memory is
\emph{not} included in any client figure. The server's cost appears instead
as its own storage, measured through \texttt{collStats storageSize} on the
benchmark database (\texttt{search\_engine\_benchmark}), and as the extra
process a deployment must run. Any capacity statement about MongoDB in this
report refers to that measured size at the measured corpus, plus the
unmeasured server memory, which is listed as a limitation.
